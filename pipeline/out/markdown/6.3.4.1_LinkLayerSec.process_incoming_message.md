# 6.3.4.1 LinkLayerSec.process_incoming_message

6.3.4.1 LinkLayerSec.process_incoming_message
This process shall handle an incoming container (for DLL receive process, see section 5.3.1) and is
executed after primitive 6.3.2.3 has been called by the DLL.
The following incoming OAM messages shall pass without checks and modifications by the link layer
security and return by primitive 6.3.2.4
•
All OAM frames/messages with KeyEx primitives
•
Enumeration messages:
o Node Discover
o Self Announce
All such incoming OAM messages shall have byte0,bit7=0 (of the Security Payload) to identify them
as unprotected by Link Layer Security.
OAM messages not listed here shall be filtered out (all arguments in 6.3.2.4 set to 0), when security is
enabled, but not yet established.
Empty OAM frames (just the OAM header, without any CADs):
- Shall pass without checks before LKs are installed
- Shall pass security after LKs are installed
All other OAM messages need to pass the security based on its current configuration. If the security
is active, all containers, except those OAM containers listed above, shall be protected.
LinkLayerSec.process_incoming_message shall do the following processing in this order:
•
If the incoming message is any of the above listed OAM messages exempt from security, skip
the remaining processing steps.
•
Determine which Key Slot state applies based on KeySwitch (Header) Flag (0 for first slot, 1
for second). The Key Slot state includes Key, Salt, and“Last Link Layer RX AEAD Invocation”
Counter as well as possible status counters.
•
Check if selected Key Slot is valid and ready. If not, drop messages and increment statistics
counter “security: dropped RX frames” by 1.
•
Construct assumed IV (see section 6.3.1.2 for IV format and section 6.3.1.3 for container
format):
o Split “Last Link Layer RX AEAD Invocation Counter” in two parts:
▪ Last Shadow Counter: | the most significant 56 bits
▪ Last Counter: | the least significant 8 bits
o If Last Counter < received Counter (see 6.3.1.3.1):
▪ Assume “AEAD Invocation Counter” for incoming containerprocessing as:
•
Last Shadow Counter as the most significant 56 bits
•
Received Counter as the least significant 8 bits
o If Last Counter >= received Counter (see 6.3.1.3.1):
▪ Assume “AEAD Invocation Counter” for incoming containerprocessing as:
•
Last Shadow Counter + 1 as the most significant 56 bits
•
Received Counter as the least significant 8 bits
•
Do crypto processing (by running AES-GMAC or AES-GCM based on configuration)
•
Check ICV:
o If this fails, drop messages, call the primitive defined in section 6.3.2.5.
o If ICV correct:
▪ Update “Last Link Layer RX AEAD Invocation Counter” with value of assumed
“AEAD Invocation Counter”.
▪ AES-GMAC: Return container without counter and ICV (see 6.3.2.4).
▪ AES-GCM: Return container with decrypted payload and remove counter and
ICV (see 6.3.2.4).
▪ Switch the active RX Key Slot, if message was received with correct ICV of the
other Key Slot. Deactivate old Key Slot.
