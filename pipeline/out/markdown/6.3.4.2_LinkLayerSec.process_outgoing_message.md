# 6.3.4.2 LinkLayerSec.process_outgoing_message

6.3.4.2 LinkLayerSec.process_outgoing_message
This process is executed after primitive 6.3.2.1 and shall handle an outgoing container and return the
Container header with a updated KeySwitch and the Security Payload as defined in Table 6-2 (for DLL
transmit process, see section 5.2.1) by primitive 6.3.2.2.

Table 6-2: Security Payload
The following incoming OAM messages shall pass without checks and modifications by the link layer
security and be returned by primitive 6.3.2.2.
•
All OAM frames/messages with KeyEx primitives
•
Enumeration messages:
o Node Discover
o Self Announce
OAM messages not listed here shall be filtered (all arguments in 6.3.2.2 set to 0), when security is
enabled, but not yet established (LKs not yet installed).
Empty OAM frames (just the OAM header, without any CADs):
- Shall pass without checks before LKs are installed
- Shall pass security after LKs are installed
All other OAM messages need to pass the security based on its current configuration. If the security
is active, all containers, except those OAM containers listed above, shall be protected.
LinkLayerSec.process_outgoing_message shall do the following processing in this order:
•
If the incoming message is any of the above listed OAM messages exempt from security, skip
the remaining processing steps.
•
In the Security Payload, set byte0, bit7=1
•
Select the Key, Salt, Next Link Layer TX AEAD Invocation Counter, and Status based on
currently selected key slot.
•
Check if selected Key Slot is "ready" or "active". If not, drop messages and increment
statistics counter “security: dropped TX frames” (see3.4.3) by 1. Call primitive 6.3.2.5.
•
Construct IV (see section 6.3.1.2 for IV format and section 6.3.1.3 for container format):
o Construct IV by concatenating the fields:
▪ KeyEx = 0
▪ Dir
